# 第17章：性能优化

Pandas 性能优化的核心不是记住“某个函数一定更快”，而是建立一套稳定流程：**先保证结果正确，再测量瓶颈，最后针对数据规模、dtype 和访问模式优化**。

## 17.1 先测量，再优化

Notebook 中可以用 `%timeit`，普通脚本可以使用 `time.perf_counter()`。

```python
import time
import numpy as np
import pandas as pd

rng = np.random.default_rng(42)
df = pd.DataFrame({
    "a": rng.normal(size=500_000),
    "b": rng.normal(size=500_000),
})

start = time.perf_counter()
result = df["a"] + df["b"]
elapsed = time.perf_counter() - start
print(f"耗时: {elapsed:.4f}s")
```

单次计时容易受缓存和系统负载影响，正式比较时应多次运行并比较分布，而不是只看一次结果。

## 17.2 优先向量化

```python
# 不推荐：逐行 Python 循环
slow = []
for row in df.itertuples(index=False):
    slow.append(row.a + row.b)

# 推荐：列级向量化
fast = df["a"] + df["b"]
```

向量化通常能把循环下沉到 NumPy/Pandas 的底层实现，并减少 Python 解释器开销。

## 17.3 避免逐行 apply 能向量化的表达式

```python
# 可以工作，但没有必要逐元素调用 Python 函数
r1 = df["a"].apply(lambda x: np.sqrt(x * x + 1))

# 更直接
r2 = np.sqrt(df["a"] ** 2 + 1)
```

`apply` 不是“错误 API”；当函数本身无法用数组运算表达时仍然有价值。优化时应先判断能否改写为列级运算。

## 17.4 选择合适的数据类型

```python
n = 100_000
data = pd.DataFrame({
    "id": np.arange(n),
    "city": rng.choice(["Nanjing", "Suzhou", "Wuxi"], size=n),
})

print(data.memory_usage(deep=True).sum())

optimized = data.astype({
    "id": "int32",
    "city": "category",
})
print(optimized.memory_usage(deep=True).sum())
```

低基数重复字符串适合 `category`；整数是否能降位宽取决于真实取值范围。不要为了省内存让数值溢出。

## 17.5 读取时就减少数据量

如果只需要部分字段，应在 I/O 阶段过滤：

```python
df = pd.read_csv(
    "large.csv",
    usecols=["id", "time", "value"],
    dtype={"id": "int32", "value": "float32"},
    parse_dates=["time"],
)
```

这通常比“全部读入后再删除列”更节省内存。生产数据还可以考虑 Parquet 等列式格式。

## 17.6 分块处理无法一次装入内存的数据

```python
parts = []
for chunk in pd.read_csv("large.csv", chunksize=100_000):
    part = (
        chunk.loc[chunk["value"] > 0]
        .groupby("category", as_index=False)["value"]
        .sum()
    )
    parts.append(part)

result = (
    pd.concat(parts, ignore_index=True)
    .groupby("category", as_index=False)["value"]
    .sum()
)
```

注意：只有能够“分块后再合并”的统计量才适合这种写法。全局排序、精确分位数等任务需要额外设计。

## 17.7 减少重复计算

```python
# 重复筛选会重复计算条件
mask = (df["a"] > 0) & (df["b"] < 1)
selected = df.loc[mask, ["a", "b"]]
```

复杂表达式、正则匹配或昂贵映射在多次使用时可以显式缓存中间结果。

## 17.8 索引不是万能加速器

`set_index()` 对按标签反复定位很有用，但建立索引本身也有成本，而且布尔筛选、聚合、顺序扫描不一定会因此更快。

```python
lookup = pd.DataFrame({
    "station_id": [101, 102, 103],
    "value": [2.4, 3.1, 1.8],
}).set_index("station_id")

print(lookup.loc[102])
```

是否建立索引应由访问模式决定。

## 17.9 不把 inplace 当作性能规则

现代 Pandas 的内存行为受到 Copy-on-Write 等机制影响，“带 inplace 参数”不等价于“一定更快”或“一定不复制”。优先写清晰、可组合、行为明确的代码，然后通过内存和时间基准验证。

```python
clean = df.dropna(subset=["a"]).assign(total=lambda x: x["a"] + x["b"])
```

这种表达式更容易组成数据处理管道，也更方便测试。

## 17.10 GroupBy：减少无关列和无关分组

```python
sales = pd.DataFrame({
    "region": rng.choice(["east", "west", "north"], size=200_000),
    "amount": rng.gamma(2, 50, size=200_000),
    "unused": rng.normal(size=200_000),
})

summary = (
    sales[["region", "amount"]]
    .groupby("region", as_index=False)
    .agg(total=("amount", "sum"), mean=("amount", "mean"))
)
```

只保留参与计算的列可以减少内存流量。

## 17.11 NumPy 边界：什么时候转数组

如果后续工作完全是数值数组计算，可以在边界处显式转换：

```python
x = df[["a", "b"]].to_numpy()
norm = np.sqrt((x ** 2).sum(axis=1))
```

转换后会失去 Pandas 的标签语义，因此不要在仍需要索引对齐的步骤中过早转成数组。

## 17.12 大于单机内存时怎么办

当数据无法合理装入单机内存时，不应继续通过微小代码技巧硬撑。可以根据任务选择：

- 分块读取与在线聚合；
- DuckDB/Polars 等面向分析的执行引擎；
- Dask 等分布式 DataFrame 工具；
- 数据库或列式存储，把过滤和聚合下推到数据层。

这里的关键是改变执行策略，而不是把 Pandas 当作所有规模数据的唯一工具。

## 17.13 性能检查清单

1. 结果是否正确？
2. 真正的瓶颈在 I/O、CPU 还是内存？
3. 能否减少读取的行和列？
4. dtype 是否合理？
5. 能否用向量化替代 Python 循环？
6. 是否在重复计算相同条件或转换？
7. 中间对象是否过多？
8. 是否适合分块？
9. 是否需要换一种数据格式或执行引擎？
10. 优化前后是否用同一数据和同一方法测量？

## 小结

Pandas 优化最可靠的优先级通常是：**减少数据量 → 合理 dtype → 向量化 → 减少中间对象 → 分块/换执行引擎 → 再考虑微观优化**。不要把某个参数、某种索引或某个函数当成无条件的性能捷径。
